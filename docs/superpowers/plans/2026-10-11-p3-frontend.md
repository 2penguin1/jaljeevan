# P3: Frontend Foundation, 3D Landing Page and Live Map: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a premium, public React frontend made of:
- a design system and app shell;
- a sculpted 3D India landing page;
- a live MapLibre/deck.gl globe;
- a zones list, a zone page and an ops page;

plus the backend read APIs and the live SSE stream that feed them, and the open P1 bug fixes.

**Architecture:**
- **Backend:** new public read endpoints under `/api/v1`. Each is a controller → query service → repository, following `2026-10-11-backend-lld.md`. A `LiveEventRelay` turns Postgres NOTIFY into SSE.
- **Frontend:** one Vite + React + TypeScript app in `frontend/`. Data flows page → feature components → TanStack Query hooks → a typed API client generated from OpenAPI. Routes are code-split, so the 3D (`three`) and map (`maplibre`/`deck.gl`) chunks load only where they are used.

**Tech Stack:**
- **Backend:** FastAPI, SQLAlchemy/PostGIS, cachetools.
- **Frontend:** Vite, React 19, TypeScript, Tailwind v4, shadcn/ui, React Router 7, TanStack Query 5, three + @react-three/fiber + drei + postprocessing, maplibre-gl 5, deck.gl 9, motion, recharts, lucide-react, openapi-typescript, Vitest + Testing Library + MSW, Playwright + @axe-core/playwright.

**Spec:** `docs/superpowers/specs/2026-10-11-p3-frontend-design.md` (product: `2026-10-10-mvp-design.md`; backend rules: `2026-10-11-backend-lld.md`).

- **Hazards are never colour-only:** icon + label always.
- **Anti-slop:**
  - no purple/blue gradients;
  - no emoji;
  - no "hero + 3 feature cards";
  - no filler copy: the landing page has one headline, one line, three live numbers and one button;
  - no stock illustrations.
- **Product name** comes from `VITE_APP_NAME` (default `"Jal"`).
- **Performance:**
  - first-load JS per route ≤ 250 KB gzip, excluding the lazy 3D/map chunks;
  - the landing poster visible in < 2 s;
  - district GeoJSON simplified and coordinates rounded to 4 dp.
- **No CORS:** Vite proxies `/api` to `http://localhost:8000` in development.
- **Accessibility:** text contrast ≥ 4.5:1, visible focus, and `/zones` as the list alternative to the map.

## Review Focus
1. **The database has no zones for a hazard** (e.g. heat in October): the map, the zones list and the landing page show designed empty states, never a blank canvas or a crash. Pinned by tests in Tasks 2, 9 and 12.
2. **The SSE connection drops or the backend restarts:** the UI shows "reconnecting" and recovers with no page reload, and the server never leaks a LISTEN connection per client. Pinned in Tasks 4 and 6.
3. **A zone id that doesn't exist, or a malformed one** (`/zones/abc`): an API 404 or 422, and the UI shows "Zone not found" with a link back. Pinned in Tasks 3 and 10.
4. **A phone, a low-end GPU or reduced-motion settings:** the landing page uses the static poster or a light mesh, and the map stays usable. Pinned in Tasks 12 and 13.
5. **Untrusted text from posts** (titles and quotes containing HTML or `<script>`) is shown as text, never as HTML. Pinned in Tasks 3 and 10.

### Task 1: P1 bug fixes from the live runs

**Files:**
- Modify:
  - `backend/app/domain/zones.py` (zone type)
  - `backend/app/domain/lifecycle.py` (RESOLVING flicker)
  - `backend/app/repositories/zone_repository.py` (temp table)

  - `backend/app/main.py` and `backend/app/cli/run_pipeline.py` (quiet the `httpx2` logger)
- Test: `backend/tests/test_p1_followups.py`

**Fixes:**
1. **Zone type:** neighbourhoods from GeoNames that lie inside an urban district (e.g. "Adyar, Chennai", stored as a village) are classified `rural`. Rule: a point inside a district whose largest town is a city of ≥ 1 M people, with a location precision of `ward` or `village` → `urban_pocket`. Implementation: the `ClusterPoint` gets a `district_urban: bool` from SQL (`EXISTS` a town with `is_urban` AND population ≥ 1,000,000 in the same `district_name`/`state_code`).
2. **RESOLVING is sticky:** it stays `resolving` while the score is < activate. It goes back to ACTIVE only when the score is ≥ activate with evidence.
3. **Temp table:** `CREATE TEMP TABLE zone_pts (...) ON COMMIT DROP`, and drop the `DROP TABLE IF EXISTS` (it could hit a real table).
4. **Single-run guard:** `IntelligencePipeline.run` takes `pg_try_advisory_xact_lock(hashtext('pipeline'))`. If the lock is held, it records `stats={"skipped": "another run in progress"}` and returns without running any stages.
5. **Reddit date window:** `RedditFetcher.run_input` sends `searchTime: "week"`, `searchSort: "new"` and `postDateLimit` (ISO date, 7 days ago). The fetcher drops rows older than 30 days **before** archiving (the paid rows are still logged in the stats).
6. **Logging:** set the `httpx2` logger to WARNING alongside `httpx`.

### Task 4: Live event relay (Postgres NOTIFY → SSE)

**Files:**
- Create: `backend/app/services/live_relay.py` (`LiveEventRelay`), `backend/app/api/v1/endpoints/live.py`
- Modify: `backend/app/main.py` (start and stop the relay in the lifespan)
- Test: `backend/tests/services/test_live_relay.py`

**Design:**
- **One** dedicated psycopg connection per process does `LISTEN signal_classified; LISTEN zone_escalated`, in a daemon thread, and fans out to subscriber `asyncio.Queue`s via `loop.call_soon_threadsafe`. There is never one LISTEN per client.
- `subscribe() -> asyncio.Queue` and `unsubscribe(q)`. Each queue is bounded at 100; a full queue drops the oldest event.
- `GET /api/v1/live` streams `text/event-stream`: `event: signal\ndata: {"id": "..."}` and `event: zone\ndata: {...}`, with a `: heartbeat` comment every 15 s. It unsubscribes on client disconnect.
